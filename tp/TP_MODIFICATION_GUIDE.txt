一、总体架构
──────────────────────────────────────────────────────────────────────────────

  张量并行（Tensor Parallelism, TP）将单层 Transformer 的权重矩阵按列或行切
  分为 4 份（对应一颗飞腾 CPU 的 4 个 NUMA 节点），每个 NUMA 节点上的进程独立
  计算自己那部分，中间通过 all-gather / all-reduce 汇总结果。

  三层改动：
    （1）权重准备层：gguf-split.py 将完整 GGUF 切为 4 个 .tp{rank}.gguf
    （2）计算图层：ggml 新增 2 个算子 + qwen3.cpp 插入通信节点
    （3）进程管理层：pipeline-brick.cpp fork 4 个子进程 + 传输代理

  设计原则：
    - TP=0 时所有新增代码路径不触发，与原版行为全兼容
    - 只影响 QWEN3 密集模型（通过 model arch 限定）
    - all-reduce/all-gather 通过 mmap 共享内存 + 自旋屏障实现，零系统调用

  【怎么改的】

    │ blk.0.attn_q.weight  [2560, 2560]                       │
    │ blk.0.attn_k.weight  [2560, 640]                        │

    │ blk.0.ffn_up.weight   [2560, 6912]                      │
    │ blk.0.ffn_down.weight [6912, 2560]                      │
    │ blk.0.attn_norm.weight [2560]          ← 全量复制        │
    │ token_embd.weight     [151936, 2560]   ← 全量复制        │
    └──────────────────────────────────────────────────────────┘
                            │
            ┌───────────────┼───────────────┬───────────────┐
            ▼               ▼               ▼               ▼
    ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
    │  .tp0.gguf   │ │  .tp1.gguf   │ │  .tp2.gguf   │ │  .tp3.gguf   │
    │              │ │              │ │              │ │              │
    │ Q[2560,640]  │ │ Q[2560,640]  │ │ Q[2560,640]  │ │ Q[2560,640]  │
    │ K[2560,160]  │ │ K[2560,160]  │ │ K[2560,160]  │ │ K[2560,160]  │

    │ O[640,2560]  │ │ O[640,2560]  │ │ O[640,2560]  │ │ O[640,2560]  │
    │ gate[2560,   │ │ gate[2560,   │ │ gate[2560,   │ │ gate[2560,   │
    │      1728]   │ │      1728]   │ │      1728]   │ │      1728]   │
    │ up[2560,1728]│ │ up[2560,1728]│ │ up[2560,1728]│ │ up[2560,1728]│
    │ down[1728,   │ │ down[1728,   │ │ down[1728,   │ │ down[1728,   │
    │      2560]   │ │      2560]   │ │      2560]   │ │      2560]   │
    │ norm[2560]   │ │ norm[2560]   │ │ norm[2560]   │ │ norm[2560]   │
    │ embd 完整    │ │ embd 完整    │ │ embd 完整    │ │ embd 完整    │
    └──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘
       rank 0           rank 1           rank 2           rank 3

    切分规则：
      - 列并行（切 numpy dim -1, GGUF 最内维）：attn_q, attn_k, attn_v,
        ffn_gate, ffn_up
      - 行并行（切 numpy dim 0, GGUF 最外维）：attn_output, ffn_down
      - 全量复制：所有 norm 权重、token_embd、output

    使用 GGUF 二进制格式读写（不依赖 gguf-py），支持 F16/F32 类型。
    量化类型（Q4_K 等）需先用 convert 工具 dequantize 为 F16。

  【为什么这么改】
    TP 要求每个 rank 只加载自己那部分权重。如果运行时切分，需要修改 llama.cpp
    的张量加载逻辑（llama-model.cpp），且需要所有 rank 共享完整权重文件的内存，
    改动量大且容易出错。提前切分成独立文件，每个 rank 用原版模型加载代码直接
    读自己的文件——零侵入 llama_model 加载路径。

四、文件 3：ggml/src/ggml.c
──────────────────────────────────────────────────────────────────────────────

  【改了什么】
    （1）GGML_OP_NAME 数组新增 "ALL_REDUCE_SUM"、"ALL_GATHER"
    （2）GGML_OP_SYMBOL 数组新增 "all_reduce_sum(x)"、"all_gather(x)"
    （3）static_assert(GGML_OP_COUNT) 从 97 改为 99
    （4）新增全局结构体 g_tp_ctx（rank/size/shm_base/barrier）
    （5）ggml_set_tp_ctx / ggml_get_tp_rank / ggml_get_tp_size 实现
    （6）ggml_all_reduce_sum / ggml_all_gather wrapper 函数实现

  【怎么改的】
    g_tp_ctx 是文件级 static 变量，存当前进程的 TP rank 和 size。
    wrapper 函数构造 ggml_tensor，把 tp_rank/tp_size 存入 op_params，
    设置 src[0] 指向输入张量。
    
    对于 all_reduce_sum：输出形状 = 输入形状
    对于 all_gather：输出形状 = 输入形状 × tp_size（沿最内维扩展）

  【为什么这么改】
    ggml.c 是所有 ggml 算子的注册和构造中心。wrapper 函数给上层提供简洁的
    C API，隐藏了内部 op_params 填充细节。g_tp_ctx 用全局变量的原因是：
    TP rank 在进程生命期内不变，全局变量最简单且不需要侵入 llama_context。

六、文件 5：ggml/src/ggml-cpu/ops.cpp
──────────────────────────────────────────────────────────────────────────────

  【改了什么】
    （1）ggml_tp_shm 全局结构体（rank/size/shm_base/barrier）
    （2）ggml_tp_shm_init() 初始化函数
    （3）tp_barrier_wait() 自旋屏障
    （4）ggml_compute_forward_all_reduce_sum() 实现
    （5）ggml_compute_forward_all_gather() 实现

  【怎么改的】
    all_reduce_sum 实现：
      phase 1: 每个 rank 把自己的数据 memcpy 到共享窗口的 [tp_rank] 槽位
      phase 2: tp_barrier_wait() 等齐所有人
      phase 3: 每个 rank 遍历所有槽位，逐元素求和
      phase 4: tp_barrier_wait() 等齐所有人读完

    all_gather 实现：
      phase 1: 每个 rank 把自己的数据 memcpy 到共享窗口的 [tp_rank] 槽位
      phase 2: tp_barrier_wait() 等齐所有人
      phase 3: 每个 rank 按 rank 顺序 memcpy 所有槽位到输出张量
      phase 4: tp_barrier_wait() 等齐所有人读完

    屏障实现：
      __sync_fetch_and_add(&counter, 1) → 最后一个到达者重置 counter → 其他
      自旋 __sync_fetch_and_add(&counter, 0) 直到 counter==0。ARM 上自旋时
      用 yield 指令降低功耗。

  【为什么这么改】
    ggml 没有内置的跨进程通信算子。自定义算子是唯一能在计算图中间插入通信
    节点的方式——ggml 图的执行流程天然保证了"算完前一层再算后一层"的顺序，
    我们在算子和算子之间插入的 all-reduce 自动满足了同步要求。


七、文件 6：ggml/src/ggml-cpu/ggml-cpu.c
──────────────────────────────────────────────────────────────────────────────

  【改了什么】
    在两处 dispatch switch 中新增 GGML_OP_ALL_REDUCE_SUM 和
    GGML_OP_ALL_GATHER 的 case 分支：
      - compute dispatch：调用 ggml_compute_forward_*() 函数
      - n_tasks dispatch：设置 n_tasks = 1（通信算子单线程执行）

  【为什么这么改】
    CPU 后端的算子调度通过 switch-case 分派。n_tasks=1 是因为 all-reduce
    内部有自旋屏障，多线程并发会导致死锁或数据竞争。

九、文件 8：src/models/qwen3.cpp
──────────────────────────────────────────────────────────────────────────────

  【改了什么】
    在 graph() 构造函数中新增 TP 分支：
    （1）读取 params.tp_size，判断是否启用 TP
    （2）build_qkv 之后，对 Qcur/Kcur/Vcur 做 all_gather
    （3）build_attn 之后，对注意力输出做 all_reduce_sum
    （4）FFN 替换为内联 TP 版本（不复用 build_ffn 基类方法）：
        - ffn_up/ffn_gate 各自做 build_lora_mm → all_gather
        - ggml_swiglu_split 做 SiLU×gate（此时 gate 和 up 都已完整）
        - ffn_down 做 build_lora_mm → all_reduce_sum
    （5）TP 未启用时，走原版 build_ffn 路径，行为完全不变

  【怎么改的】伪代码对比如下

    原版（单层循环）：
      for il in [layer_start, layer_end):
        Q,K,V = build_qkv(cur)        → 一次性算出完整 Q/K/V
        cur  = build_attn(Q,K,V)      → 算注意力 + O 投影
        cur  = build_ffn(cur)         → SwiGLU + 下投影

    TP 版（单层循环）：
      for il in [layer_start, layer_end):
        Q,K,V = build_qkv(cur)        → 各 rank 算部分 Q/K/V
        Q = all_gather(Q)             → 拼成完整 Q  [n_tok, 2560]
        K = all_gather(K)             → 拼成完整 K  [n_tok, 640]
        V = all_gather(V)             → 拼成完整 V  [n_tok, 640]
        cur = build_attn(Q,K,V)       → 用完整 Q/K/V 做注意力，O 输出 [n_tok, 640]
        cur = all_reduce_sum(cur)     → 各 rank 求和 → 完整 hidden [n_tok, 2560]

        gate = matmul(cur, W_gate_local)  → [n_tok, 1728]
        up   = matmul(cur, W_up_local)    → [n_tok, 1728]
        gate = all_gather(gate)           → [n_tok, 6912]
        up   = all_gather(up)             → [n_tok, 6912]
        hidden = swiglu(gate, up)         → [n_tok, 6912]
        down = matmul(hidden, W_down_local) → [n_tok, 2560]（各 rank 部分和）
        cur = all_reduce_sum(down)        → 完整 hidden [n_tok, 2560]

  【为什么这么改】
    - 复现 build_ffn 而非改造：build_ffn 是 llm_graph_context 基类方法，
      被 30+ 个模型架构共用。改造它有全局影响风险。内联 TP 版本仅影响
      QWEN3 且仅在 TP 模式触发。
    - all-gather Q/K/V 之后再算注意力：各 rank 只有部分 Q 头（8 个 / 32），
      需要拼成完整 Q 才能让注意力计算正确（需要所有 Q 头与所有 KV 头交互）。
    - all-reduce 放在 O 投影和 FFN down 之后：因为 O 和 down 是行并行——
      每个 rank 产出完整 hidden_size 维度的"部分和"，需要累加。


十、文件 9：tools/pipeline-brick/pipeline-brick.cpp
───────────────────────────────────────────────────────────────────────────────

  【改了什么】

    A. 原有改动（cxl_transport，在 TP 之前已完成）
       - transport_kind 枚举新增 cxl
       - ntb_mw_transport 旁边新增 cxl_transport 类（去 doorbell + NUMA 绑定）
       - run_head/run_tail 模板化

    B. TP 进程管理（本次新增）
       - ggml_tp_shm_init 外部声明
       - tp_transport_proxy<Transport> 模板类
       - make_tp_model_path / tp_shm_size 辅助函数
       - run_hardware_tp() 函数
       - run_hardware() 中 numa_tp>1 时跳转到 run_hardware_tp()

  【怎么改的】

    tp_transport_proxy<Transport>：
      包装任意 Transport 类型，提供完全相同的接口。
      - send_* 方法：仅 rank 0 实际发送，rank 1-3 跳过
      - recv 方法：
          rank 0：从 real transport 接收 → 写 header+payload 到 TP shm 广播区
                 → atomic_store ready=1 → 返回
          rank 1-3：spin-wait ready==1 → 从 TP shm 广播区读 header+payload → 返回

    run_hardware_tp()：
      ① 计算 TP 共享内存大小，mmap(MAP_SHARED | MAP_ANONYMOUS)
      ② 共享内存分 3 区：[广播区(1MB)][ready flag(4B)][all-reduce 区(~4MB)]
      ③ for r in 0..tp_size-1: fork()
      ④ 子进程：bind_to_cpus(该 NUMA 的 CPU 列表)
                → 拼接模型路径 .tp{r}.gguf
                → ggml_tp_shm_init(r, tp_size, ar_buf, ar_size)
                → ggml_set_tp_ctx(r, tp_size)
                → 创建 transport，用 tp_transport_proxy 包装
                → run_head / run_tail
      ⑤ 父进程 waitpid 所有子进程，munmap 共享内存

    TP 共享内存布局：
      +0        : [tp_bc_buf]     广播缓冲区（rank 0 写，其他 rank 读）
      +bc_size  : [tp_ready]      volatile int，ready flag（原子读写）
      +bc_size+64: [tp_ar_buf]    all-reduce 工作区（ggml TP ops 使用）

  【为什么这么改】
    - fork 而非多线程：每个 TP rank 需要独立的 GPU/tensor 上下文和不同的
      权重文件，线程模型在 ggml 中难以隔离。fork 继承父进程的 mmap 映射，
      子进程天然共享 TP 通信缓冲区。
    - tp_transport_proxy：管道传输（h2t/t2h）是 1:1 的（head brick ↔ tail
      brick），但 TP 有 4 个进程。代理让 rank 0 独占用管道，其他 rank 通过
      共享内存收数据，避免了重复发包。
    - 共享内存用 mmap 而非 shm_open：fork 子进程自动继承匿名 mmap 映射，
      无需文件系统路径，实现更简洁。
