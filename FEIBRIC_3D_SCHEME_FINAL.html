Feibric three-level parallel scheme: QPI TP-1, CXL TP-2, RDMA PP

Feibric 三级并行方案

TP-1: QPI TP-2: CXL PP: RDMA   |   4x FT4000 · 2 Domain × 2 CPU · Domain 间 RDMA 直连

一、硬件拓扑

4 块 FT4000 CPU 分属两个 Domain，通过三种链路互联。每个 Domain 内只有 2 台 CPU。

Domain A（Linux 实例 1）
CPU 0NUMA 0–364 核 128 GB
CPU 1NUMA 4–764 核 128 GB
CPU 内: QPI   CPU 间: CXL
Domain B（Linux 实例 2）
CPU 2NUMA 8–1164 核 128 GB
CPU 3NUMA 12–1564 核 128 GB
CPU 内: QPI   CPU 间: CXL
Domain A   ↔   RDMA 直连（独立地址空间，send/recv）  ↔   Domain B
关键约束：每个 Domain 只有 2 台 CPU。这决定了 CXL 方向的并行度上限为 2，以及 QPI 方向必须承担全部集合通信。

三种链路对比

链路连接范围带宽延迟地址空间通信方式
QPICPU 内 NUMA 间~50 GB/s~0.1 us共享load/store
CXLDomain 内 CPU 间~15 GB/s~1.5 us共享load/store（需 mbind）
RDMADomain 间25–100 Gbps~5 us独立send/recv（ibverbs）

二、两级张量并行（Domain 内）

与 report.pdf 一致：本节严格遵循"多级CPU张量并行分解方案技术调研报告"的 2D SUMMA 设计。所有集合通信（All-Gather、All-Reduce）限制在 QPI 域内，CXL 仅承担激活值子集分发。

2.1 2D SUMMA 网格：R=2, C=4

一个 Domain 内 8 个 NUMA 组织为 2×4 网格（R=2 为 CXL 方向，C=4 为 QPI 方向）：

行 0 = QPI 域（CPU 0）
NUMA 0   NUMA 1   NUMA 2   NUMA 3
4 个单元 · 全部在 CPU 0 上 · QPI 互联
行 1 = QPI 域（CPU 1）
NUMA 0   NUMA 1   NUMA 2   NUMA 3
4 个单元 · 全部在 CPU 1 上 · QPI 互联
行 0 ↔ 行 1 之间：CXL 链路（跨 CPU）  |   每个对应 NUMA 对 (r,c) 由 CXL 连接
参数含义值物理链路
R行数（CXL 方向）2Domain 内 2 个 CPU
C列数（QPI 方向）4每 CPU 内 4 个 NUMA
N总并行单元8Domain 内全部 NUMA
为什么 R=2, C=4 而不是反过来？QPI 域必须只包含同一 CPU 内的 NUMA。如果让 C=2（把跨 CPU 的两个 NUMA 放在同一行），行内 All-Gather 就会穿过 CXL，违反了 report 的核心设计原则。R=2（跨 CPU）× C=4（同 CPU 内 4 NUMA）确保每行内部通信走纯 QPI。

2.2 TP-1（QPI 方向，C=4）：沿隐藏维度切分

每 CPU 内 4 个 NUMA 各持有输入/输出通道的 1/4。所有 All-Gather 和 All-Reduce 在同 CPU 的 4 个 NUMA 之间通过 QPI 完成。

2
沿 QPI 方向（C=4）切扩展维度 4h：每单元 1728 维

2行内 All-Gather：拼接 C=4 个单元的 1728 维输出 → 完整 6912 维7 KB/行QPI

CXL 仅在 W&sub2; 的 Step 4 中涉及：每个节点需要 GeLU 输出的对应子集（基于其列位置），由 CXL 分发少量激活值数据。此项通信量极小，非集合操作。

2.3 TP-2（CXL 方向，R=2）：沿注意力头切分

Attention 模块 · 32 注意力头

32 头 → 8 单元 → 每 NUMA 4 个头

步骤操作通信
1每单元独立计算自己的 4 个头的 Q/K/V 投影（无通信）—
2每单元独立计算 4 个头的 Attention（无通信）—
3输出投影 O¹⁷ᴰ¹ = Attn · WO¹⁷ᴰ¹—
4行内 All-Reduce（QPI）：聚合 C=4 个 NUMA 的部分输出QPI

Attention 核心计算（QKV 投影 + softmax）完全无跨单元通信，因为不同注意力头天然独立。CXL 在 Attention 模块中不参与任何集合通信。

所有集合通信在 QPI 上完成，占总计算时间 < 3%。 CXL 仅用于分发激活值子集（非集合操作），通信量最小。这与 report.pdf 的设计原则完全一致。

三、第三级：RDMA 流水线并行（Domain 间）

本节为 Feibric 在 report.pdf 基础上的原创扩展。report.pdf 仅覆盖单个 Domain 内的 2D TP，未讨论多 Domain 场景。此处引入 RDMA 流水线并行以充分利用 4 CPU 硬件资源。

3.1 层分配

Domain A：Head
Layers 0–17（18 层）
含 Embedding 层
每层做 2D TP（R=2, C=4）
Domain B：Tail
Layers 18–35（18 层）
含 LM Head
每层做 2D TP（R=2, C=4）

切分点位于 Layer 17/18：36 层对半分保证负载均衡；不跨越特殊层结构；单次 hidden state 传输，通信量最小。

3.2 为什么走 RDMA

两个 Domain 是独立 Linux 实例 — 物理上没有共享内存。必须在网络传输方案中选择：

方案延迟适用性
TCP socket~50 us延迟过高
RDMA（ibverbs）~5 us最优选择
CXL不可用CXL 跨不了独立 OS

每 token 仅传输 1 次 hidden states（2560 × BF16 = 5 KB），带宽需求极低。延迟是唯一关键指标，RDMA 的 5 us 是最优解。

3.3 双缓冲与延迟隐藏

时刻Slot 0Slot 1
Token NDomain A 写入 → RDMA → Domain B 读取空闲
Token N+1空闲Domain A 写入 → RDMA → Domain B 读取

当 Domain A 向 Slot 0 写入并启动 RDMA SEND 后，立即开始计算下一个 token 的 Layer 0。 RDMA 的 5 us 传输时间完全被 Domain A 的 ~150 us Layer 0 计算覆盖，端到端延迟中不可见。

五、QPI × CXL 的设计必然性

QPI 承担全部集合通信

report.pdf 明确指出 All-Gather 和 All-Reduce 必须限制在 QPI 域内。一个"QPI 域"定义为同一 CPU 内的 NUMA 集合。为此选择了 R=2, C=4 的网格布局，确保每行（QPI 域）的 C=4 个单元全在同一 CPU 内。

CXL 只做轻量分发

Domain 只有 2 个 CPU（R=2），CXL 方向的设备数先天有限。这恰好匹配 CXL 的定位 — 不承担高频集合通信，只做低频率的激活值子集分发。每层 CXL 通信仅 1 次，数据量 ~3.5 KB，总开销 < 2 us。

RDMA 填补 Domain 间的空白

两个 Domain 之间不存在共享内存，必须走网络。PP 每 token 只传 5 KB，RDMA 的低延迟（5 us）是关键选择因素。双缓冲设计确保传输延迟完全隐藏在计算中。

八、设计原则总结

#原则体现
1 集合通信不离开 QPI R=2, C=4 保证每行全在同一 CPU 内；All-Gather、All-Reduce 在 QPI 域执行
2 通信量与链路带宽匹配 高频大通信 → QPI（50 GB/s）；低频轻通信 → CXL（15 GB/s）；极稀疏通信 → RDMA
3 并行度不超过物理边界 C=4 = 每 CPU NUMA 数；R=2 = Domain CPU 数；PP stage=2 = Domain 数
4 传输隐藏在计算中 RDMA 双缓冲，5 us 传输被下一 token 的 Layer 0 计算覆盖（~150 us）
